# Translate Agent Loop 对比实验分析，以及agent loop架构在 Wenyi 中的扩展潜力

## 一、Translate Agent Loop 与固定 Pipeline 的对比实验

为了判断 Agent Loop 是否能够真正承担长篇翻译任务，我们在同一段连续长文本上运行了
两套流程：实验性的 Translate Agent Loop，以及由 Translate、Polish 和 Glossary
Extraction 组成的固定 Pipeline。

这次实验首先关注的不是自动评分或反复优化译文，而是翻译过程能否由 Agent 动态组织：
Agent 是否可以完成连续 batch 的翻译，维护跨 batch 的章节记忆和术语状态，并在明确的
程序约束下提交可回填的最终译文。

### 1. 实验设计

测试文本取自 Alexei Yurchak 的 _Everything Was Forever, Until It Was No More_，包含
一个连续长章节，共分为 13 个 batch、97 个 segment。两套流程使用相同的
`deepseek-v4-flash` 模型、相同的原文切分、初始术语、风格要求和全书概览。

固定 Pipeline 对每个 batch 依次执行翻译、润色和术语抽取。Agent Loop 则为每个 batch
启动一次有界循环，并向 Agent 提供保存和修改草稿、更新章节记忆、增加术语、向人类
提问以及提交译文等能力。Agent 可以根据当前文本选择是否调用这些能力，但最终译文仍
必须通过确定性校验：译文数量与原文 segment 数量一致，每项都是非空字符串，并按编号
顺序对应。只有成功提交后，当前 batch 的译文和状态变化才会正式生效。

实验记录了两套流程的运行时间、输入和输出 Token、缓存命中、估算费用、最终术语表，
以及 97 个 segment 的最终译文。更详细的配置与复现信息见
[实验说明](EXPERIMENT_AGENT_VS_PIPELINE.md)，完整术语和译文对照见
[对照报告](AGENT_PIPELINE_COMPARISON.md)。

### 2. 实验结果

两套流程都成功完成了全部 13 个 batch，提交了 97 条译文，没有出现中断或 segment
数量不一致。

| 指标             | Agent Loop | 固定 Pipeline |
| ---------------- | ---------: | ------------: |
| 成功 batch       |      13/13 |         13/13 |
| 成功 segment     |      97/97 |         97/97 |
| 输入 Token       |    234,718 |       131,226 |
| 输出 Token       |    125,177 |       236,340 |
| 总 Token         |    359,895 |       367,566 |
| 缓存命中 Token   |    139,008 |        40,576 |
| 缓存未命中 Token |     95,710 |        90,650 |
| 缓存命中率       |     59.22% |        30.92% |
| 估算费用         |      ¥0.35 |         ¥0.56 |
| 最终术语数量     |         35 |           257 |
| 运行时间         |   1,088 秒 |      2,144 秒 |

费用按照本次实验时的 DeepSeek V4 Flash 价格计算：缓存命中输入每百万 Token 0.02 元，
缓存未命中输入每百万 Token 1 元，输出每百万 Token 2 元。Agent Loop 的完整运行费用约
为 0.349 元，固定 Pipeline 约为 0.564 元，前者低约 38%。

运行时间只作为探索性数据。LLM 思考长度和服务响应时间存在明显波动，而且本次
Pipeline 前三个 batch 曾与一个意外重复启动的同配置进程同时运行，因此不能根据这一次
结果稳定地推断速度比例。Token、费用和最终输出均来自各自保存下来的单一完整 trace。

### 3. 成本差异来自 Token 结构

从总 Token 看，两套流程的差距并不大。Agent Loop 使用 359,895 Token，固定 Pipeline
使用 367,566 Token，只相差约 2%。真正产生费用差异的是 Token 的组成。

| 费用构成       |  Agent Loop | 固定 Pipeline |
| -------------- | ----------: | ------------: |
| 缓存命中输入   |     ¥0.0028 |       ¥0.0008 |
| 缓存未命中输入 |     ¥0.0957 |       ¥0.0907 |
| 模型输出       |     ¥0.2504 |       ¥0.4727 |
| 合计           | **¥0.3488** |   **¥0.5641** |

Agent Loop 的输入 Token 明显更多，因为 Tool 定义、当前状态和循环历史会再次进入模型
上下文。但其中有 139,008 Token 命中了缓存，按照当前价格，这部分只产生约 0.003 元
费用。两套流程的缓存未命中输入成本实际上非常接近：Agent Loop 约 0.096 元，固定
Pipeline 约 0.091 元。

真正拉开差距的是输出 Token。固定 Pipeline 产生 236,340 个输出 Token，而 Agent Loop
只有 125,177 个。固定 Pipeline 中 Translator 产生 116,711 个输出 Token，Polisher 又
产生 105,744 个，Glossary Extractor 产生 13,885 个。Polisher 虽然只接收已有译文并
进行二次加工，仍然产生了接近重新执行一次 Translator 的输出及思考成本。

Agent Loop 没有把完整的二次润色规定为每个 batch 必须经过的独立阶段。翻译、状态
判断和必要修改发生在同一个有界循环中。它因此使用了更多上下文输入，却避免了大量固定
发生的第二次强档输出。

本次实验表现出的经济性不是简单的“少用 Token”，而是：

> Agent Loop 将一部分计算从高价的重复生成转移到低价且可以命中缓存的上下文输入，
> 并避免每个 batch 都进行一次完整的输出型后处理。

这一优势依赖具体模型的推理行为、缓存策略和 Token 定价，不能直接推断到所有供应商和
模型。但在当前 DeepSeek V4 Flash 的价格结构下，它形成了实际的费用优势。

### 4. 译文质量与动态状态的效果尚待验证

两套流程都完成了 13 个 batch、97 个 segment，并满足相同的结构化输出要求。这证明
Translate Agent Loop 已经能够运行完整的连续翻译任务，但不能证明它产生了更好的
译文。

97 个 segment 中，两套流程只有 8 个最终译文完全相同。固定 Pipeline 的 Polisher 修改
了 61 个 segment。但无论是字符串差异，还是润色阶段产生了修改，都不能直接说明哪一个
版本更准确、更连贯或更适合出版。当前结果还没有经过系统性的人工盲评。

实验 trace 可以确认 Agent 在翻译过程中更新了章节摘要和术语，新状态也进入了后续
batch 的输入。但当前没有设置“启用动态状态”与“禁用动态状态”的对照组，因此无法判断
这些状态更新是否实际改善了后文译文。

现阶段能够确认的是机制已经运行：Agent 可以维护跨 batch 状态，已提交状态可以进入
后续 batch，未提交状态不会污染后文。但“动态章节记忆是否提高长距离连贯性”“新增术语
是否改善后文一致性”仍然是假设，需要有针对性的消融实验或人工评估。

### 5. Agent Loop 抽取术语的行为差异

虽然术语状态的实际翻译收益尚未得到验证，两套流程在“什么内容会被记录为术语”方面
已经表现出明显差异。

固定 Glossary Extractor 在每个 batch 上执行一次，最终得到 257 项术语。Agent Loop
则由模型在翻译过程中判断是否需要记录术语，最终保留 35 项。经过 source normalization
后，两边共有 26 项，其中 15 项译法相同、11 项译法不同；仅 Agent Loop 存在 9 项，
仅固定 Pipeline 存在 231 项。

Agent Loop 记录的内容较集中于对章节理解和后续译法有持续影响的理论概念，例如：

- `authoritative discourse`：权威话语
- `performative shift`：述行性转向
- `Imaginary West`：想象性西方
- `metadiscourse`：元话语
- `obshchenie`：交往

固定 Extractor 的术语表覆盖范围更广，除理论概念外，还包括大量人物、作品、组织、
地点和一般表达。这说明两种机制对术语表的理解不同：固定 Extractor 更接近系统抽取
当前原译文中的实体和表达，Agent Loop 则更倾向于记录它判断会影响后续翻译决策的内容。

不能仅凭数量断言哪一种更好。人物和作品名称同样可能需要长期保持一致，较小的术语表
也可能遗漏重要实体。此外，本次固定 Pipeline 基线没有接入正式 glossary DB 中的重复
出现过滤、历史译法校准和完整冲突处理，257 项不能直接等同于正式 Wenyi 的最终术语库。

本次结果能够支持的结论是：Agent Loop 已经表现出对长期翻译状态进行选择的行为，而
不是机械地把每个 batch 的抽取结果全部加入术语表。这种选择是否更好，还需要结合人工
检查和更多文本继续评估。

### 6. 实验小结

本次实验最明确的优势体现在 Token 使用的经济性。在总 Token 基本相同的情况下，Agent
Loop 减少了高价的输出 Token，并利用了更多可缓存输入，使完整运行费用从约 0.56 元
下降到约 0.35 元。

实验还观察到 Agent Loop 与固定 Extractor 在术语选择上的显著差异：前者产生了更小、
更偏向核心概念的状态集合，后者提供了更广泛的实体和表达覆盖。但目前还不能据此判断
哪一种术语策略最终带来更好的翻译。

至于动态章节记忆、即时术语更新和人工介入，它们目前首先是已经实现的架构能力。它们
具有改善长篇翻译连贯性和人机协作的潜力，但这种潜力仍需进一步实验验证，不应作为本次
对比已经证明的结果。

## 二、Agent Loop 在 Wenyi 整体流程中的潜力

### 1. 什么是 Agent Loop

固定 Pipeline 在运行前就决定模型调用的顺序。Agent Loop 则把一个有明确边界的任务
交给模型，并提供一组可以调用的 Tool。模型读取当前任务和状态，选择下一步操作，获得
Tool 返回结果，再决定后续动作，直到提交最终结果。

```text
固定 Pipeline：调用 A → 调用 B → 调用 C → 输出

Agent Loop：读取任务 → 选择 Tool → 读取结果 → 继续操作或提交
```

两者的区别不在于是否使用 LLM，而在于流程决策是在什么时候作出的。固定 Pipeline 在
开发阶段预先决定调用顺序；Agent Loop 允许模型在运行时根据当前任务选择需要的能力。

Agent Loop 并不意味着把整个项目交给一个可以自由行动的模型。Wenyi 更适合的模式是：

> 人为制定小边界，让 Agent 在边界内部自主决策。

边界由程序定义，包括任务范围、可见信息、可用 Tool、允许修改的状态、最大轮数和最终
校验条件。Agent 只能在这些边界内决定先做什么、是否需要更多信息，以及何时提交结果。

### 2. Wenyi 中 Agent Loop 的基本模式

目前的 Translation Loop 和 Review Loop 已经提供了两个不同的例子。

Translation Loop 以一个翻译 batch 为边界。程序决定本批包含哪些 segment，并提供
当前术语、风格、章节记忆和局部上下文。Agent 可以保存或修改译文、更新章节记忆、增加
术语、向人类提问，最后提交与原文逐段对应的译文。

Review Loop 以一个审校块或一组候选问题为边界。程序提供当前原译文和可以访问的证据
能力，Agent 可以根据问题决定是否需要进一步取证，并在有限轮次内形成最终判断。

两者的业务任务不同，但遵循相同的模式：

```text
人为划定任务边界
        ↓
构造当前任务的输入与状态
        ↓
提供阶段专属 Tool
        ↓
Agent 在有限轮次内选择操作
        ↓
程序校验并提交最终结果
```

人和普通代码负责定义边界，Agent 负责处理边界内部无法提前完全枚举的决策。这是一种
介于固定 Pipeline 与完全自主 Agent 之间的设计：它保留了固定流程的可控性，又允许模型
根据具体文本调整执行路径。

### 3. 用 Agent Loop 重新组织三个阶段

基于这一模式，Wenyi 的 Prepare、Translate 和 Review 可以被组织为三个边界明确的
Agent Loop 阶段。

```text
Prepare Agent Loop
        ↓
Prepared State
        ↓
Translate Agent Loop
        ↓
Translation State
        ↓
Review Agent Loop
        ↓
Reviewed Result
```

外层阶段顺序仍然是确定的。Prepare 完成后进入 Translate，翻译完成后进入 Review。
Agent 的自主性只存在于各阶段内部。

#### Prepare Agent Loop

Prepare 阶段仍由普通代码完成文档解析、章节识别和 segment 切分等确定性任务。在此基础
上，可以把需要模型判断的准备任务放入小边界 Agent Loop，例如分析文本风格、生成全书
或章节概览、识别初始术语，以及在信息不足时选择性分析其他章节。

这一阶段提交的产物是结构化的 `Prepared State`，供后续翻译使用。它可以包含语言、
风格、全书概览、章节概览和初始术语。

#### Translation Agent Loop

Translate 阶段继续以 batch 为小边界。每个 batch 独立运行一次 Agent Loop，并读取
已经提交的翻译状态。Agent 完成当前译文，同时根据文本决定是否更新章节记忆、增加或
查询术语、查看更早上下文、修改局部译文或请求人工判断。

每个 batch 成功提交后，译文和允许更新的状态进入下一批。这样既避免跨 batch 消息历史
无限增长，也使新的理解能够逐步积累。

#### Review Agent Loop

Review 阶段继续以审校块或候选问题为小边界。Agent 不必一次读取整本书，而是根据当前
问题按需获取相关证据，并提交核验后的审校结果。对于跨章节的一致性问题，可以通过证据
Tool 查询其他位置，而不必把全书内容预先放入每次请求。

三个阶段由各自的输入、状态和 Tool 保持业务独立，同时复用相同的 Agent Loop 运行模式。

### 4. 这种架构的优势

#### 统一基础机制，降低维护成本

三个阶段的业务逻辑不同，但都需要处理模型消息循环、Tool 调度、最大轮数、working
state、最终提交、trace、Token 统计、协议错误、回退和人工输入等共同问题。

这些机制可以由一个精简的 Agent Loop 运行框架统一提供。各阶段只定义自己的 Input、
State、Toolbox、Output 和校验规则。统一的不是三个阶段的 Prompt 和业务代码，而是
它们运行 Agent 的方式。模型协议、Tool Calling、trace 或 usage 统计发生变化时，可以
在共同机制中维护，不需要在每个阶段分别处理。

#### 简化上下文管理

在固定 Pipeline 中，开发者需要为每一次模型调用提前决定应该注入哪些上下文。随着功能
增加，Translator、Polisher、Glossary Extractor 和 Reviewer 都可能需要不同组合的全书
概览、章节摘要、前文译文、术语表和历史证据。

Agent Loop 仍然需要定义信息边界，但不必把所有可能有用的信息都放进每次请求。程序只
需要决定当前任务必须直接看到什么、当前阶段允许访问什么，以及哪些信息可以通过 Tool
按需获取。

例如，Translation Agent 默认只看到当前 batch 和精简状态，在遇到人物、术语或前后文
疑问时查询历史译法或更早上下文。Review Agent 也可以只在某个问题需要核实时获取全书
证据。

因此，上下文管理从“每次调用应该塞入哪些信息”，转变为“当前阶段允许通过哪些接口访问
哪些信息”。上下文来源可以独立扩展，也不需要自动增加所有模型请求的长度。

#### 根据实际任务分配模型计算

固定 Pipeline 对每个 batch 执行相同的模型阶段。Agent Loop 可以根据当前文本决定是否
需要更新状态、查询证据、修改译文或请求人工协助。第一部分的实验已经显示，在当前
DeepSeek V4 Flash 的价格结构下，这种方式避免了大量固定发生的输出型计算，使费用降低
约 38%。

这不保证 Agent Loop 在所有模型和任务上都更便宜，但它提供了按需分配计算资源的可能：
简单文本可以较快提交，复杂文本才使用更多能力和循环轮次。

#### 更容易增加新的能力

在多阶段 Agent Loop 中，新能力可以表现为某个阶段的 Tool，例如 Prepare 阶段的资料
检索、Translate 阶段的历史译法查询、Review 阶段的跨章节证据检索，或者任意阶段的人工
确认。只要 Tool 有明确输入、输出和权限，它就可以加入相应阶段，而不需要预先决定它在
所有任务中必须执行的位置。

#### 保留确定性控制和可观测性

Agent Loop 的动态性只存在于人为划定的边界内部。阶段顺序、状态持久化、Tool 权限、
最大轮数和最终输出契约仍由程序控制。每一轮模型输入、输出、Tool 调用、状态变化和
Token 使用都可以进入统一 trace。

这种设计形成了新的职责分工：

> 外层流程负责阶段与边界，Agent Loop 负责边界内部的动态决策，Tool 和状态协议负责
> 连接两者。

Translation Loop 和 Review Loop 已经分别说明这一模式可以用于正文翻译和审校取证。
如果 Prepare、Translate 和 Review 进一步采用相同的基础运行机制，Wenyi 就可以形成
一套边界清晰、上下文按需访问，并且便于持续扩展的多阶段 Agent Loop 架构。
