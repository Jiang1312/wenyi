# Agentloop 术语方案探索记录

日期：2026-07-31

## 当前 Agent Loop 基本框架

```text
Chapter ──取出 sources──→ Sources Batch
                                ↓
  共享 TranslationState ──→ Agent Loop ←→ Tools
    章节概览 + 术语表             ｜         │更新
            ↑────────────────────────────┘
                               ↓
                           Targets
                                ↓
                           下一个 Batch
```

每次从 Chapter 中取出一组 sources，并结合共享 `TranslationState` 启动一个 Agent
Loop。Loop 中的 Tool 可以更新章节概览和术语表，提交 targets 后结束。下一个 batch
再从更新后的 `TranslationState` 开始新的循环。

## 一、最初方案：LLM 自动写入，submit 时严格校验

最初的术语方案由两个部分组成。

第一，LLM 在翻译过程中自行判断哪些表达值得记录，并通过
`add_glossary_terms` 将 source 和 target 写入共享术语表。新术语从下一个 batch
开始进入翻译输入，用于保持前后译法一致。

第二，`submit_translation` 对术语执行确定性校验：如果当前原文中出现了已有术语的
source，译文中就必须出现该术语规定的 target。校验失败时，Agent 必须修改译文后才能
提交。

这个方案隐含了一个前提：LLM 写入术语表的结果足够准确、术语的 source 和 target
足够稳定，因而可以直接转化为程序能够强制执行的规则。

实际实验说明，这个前提并不成立。

### 1. LLM 对术语边界的判断不稳定

LLM 有时记录单个词，有时记录包含该词的短语。例如 `performative` 还可能以
`performative action`、`performative dimension`、`performative shift` 等形式出现。
这些表达彼此相关，却不一定适合共享一个可机械替换的 target。

### 2. source 会发生词形和格式变化

严格匹配无法自然处理以下关系：

- `hegemony` 与 `hegemonic`；
- `late socialism` 与 `late-socialist`；
- `performative` 与 `performativity`；
- 弯引号、连字符、软连字符和异常空白造成的格式差异。

如果只做严格 source 匹配，已有术语经常无法进入真正需要它的 batch；如果不断扩大
匹配规则，又会逐渐形成一套复杂而仍不完整的词法系统。

### 3. target 不是可以脱离语境强制插入的字符串

同一个 source 在不同句法结构中可能需要不同形式。v1.1 中 `constative` 的动态译法
就是典型案例：一条偶然写入的 target 被提交校验当成固定字符串，随后迫使 Agent
修改本来可以成立的译文。严格校验没有修正严重翻译错误，反而把术语抽取阶段的不稳定
判断放大成了提交障碍。

### 4. 术语校验只能检查字符串，不能检查真正的一致性

程序可以判断某个 target 是否出现，却不能判断它在当前语境中的含义是否正确、表达
是否自然，也不能可靠处理省略、改写、复合短语和派生词。规则看起来很严格，但它所
保证的只是字符串存在，不是翻译质量。

## 二、试图解决问题的几种设想

发现上述问题后，我们讨论了几种可能的补救方案。

### 1. 加强格式归一化

首先处理 Unicode 兼容字符、大小写、弯引号、连字符、软连字符、连续空白和括号周围
空白。这能解决纯格式造成的漏匹配，是明确且低风险的改进，但不能解决词形变化和语境
差异。

### 2. 候选术语表与延迟确认

一种设想是暂不正式确认术语，只记录 LLM 认为值得关注的 source、出现位置、语境和
当前译法。等一个 chapter 甚至整本书结束后，再统一合并术语并重译受影响的位置。

这种办法避免了过早确定译法，却把问题推迟到了最后。像 `performative` 这样的高频概念
可能出现几十次，小说人物名则可能出现几百次。若最终发生调整，回改范围可能接近重新
翻译整本书。

### 3. 在术语变化后回滚此前译文

也曾考虑在新信息改变术语判断后，定位旧译文并自动重译。这需要持续记录每个术语的
出现位置、版本和影响范围，还要解决新的译文是否再次引发其他术语变化。它会把当前的
简单 Agent Loop 变成复杂的依赖与回滚系统。

### 4. 术语族、alias、note 和冲突记录

另一种方向是把相关表达组织成术语族。例如让 `performative` 和
`performative action` 属于同一族，或者像 Wenyi 一样通过 alias、note 和冲突记录保存
同一术语的不同形式与译法。

这可以保留更多信息，但随后必须继续定义：如何判断属于同一族、是否存在主项、不同
target 如何选择、旧成员如何合并，以及何时触发重译。术语表本身会逐渐成为需要 LLM
反复维护的复杂知识库。

### 5. 不断增加校验规则

还可以为复数、派生词、短语包含关系和 target 变体分别添加规则。但自然语言中的情况
无法穷尽，而本项目本来就是 LLM Agent 实验。用越来越多的硬规则修补 LLM 生成结果，
会使框架的主要精力转向维护一个不完整的术语检查器。

## 三、关键的转变：完全依赖 LLM 的指令遵循，抛弃 submit 校验和重译

讨论中的关键转变，是不再把术语表看成一组必须由程序强制执行的替换规则。

现代 LLM 已具有较强的指令遵循能力。在一个 batch 的翻译输入中，只要明确提供当前
原文相关术语及其说明，模型通常能够参考已有译法并结合具体语境进行表达。即使出现
少量差异，也不意味着应该拒绝整批译文。

因此，当前方案作出以下取舍：

- 术语表只向 LLM 提供参考，不再由 `submit_translation` 执行 source/target 字符串
  校验；
- 不因术语变化自动回滚或重译此前已经提交的内容；
- 允许 LLM 根据句法和语境调整具体表达；
- 接受术语抽取和使用存在少量波动；
- 只有出现真实、重复且明显影响翻译质量的问题时，才考虑增加新的机制。

这不是放弃术语一致性，而是把一致性的实现方式从“程序拒绝不符合字符串规则的译文”
改为“向 LLM 提供足够、相关的翻译记忆，由模型遵循”。

## 四、关于维护术语表的设想

取消硬校验后，一个自然的问题是：是否还需要认真维护术语表？如果最终完全依赖 LLM，
是否可以让术语表随意增长？

我们讨论过将单个术语改成术语族，由 LLM 在 `add_glossary_terms` 时自主决定创建新族，
还是加入已有术语。例如 `performative` 与 `performative action` 可以放在一起；同一族
内部不设主从关系。

但 `hegemony` 与 `hegemonic` 暴露了更基础的问题：即使数据层已经记录了
`hegemony`，如果构造当前 batch 输入时只进行严格匹配，遇到 `hegemonic` 仍然不会把
已有译法提供给模型。建立术语族只能在已知两者相关之后发挥作用，无法自然解决新词形
第一次出现时的检索问题。

因此，当前没有继续设计术语族，也没有要求 Agent 每次读取完整术语表进行合并。完整
术语表可以保持简单，继续保存 Agent 当时判断值得记录的 source、target 和少量说明。
同一词族被分别记录是可以接受的，例如 v1.2 中同时出现：

- `deterritorialized` → `去疆域化的`；
- `deterritorialize` → `去疆域化`。

当前不试图在写入阶段彻底整理这些关系，而是在使用阶段进行宽松检索。

## 五、术语表在指令遵循场景下的作用是什么？

术语表的价值不是验证，而是跨 batch 记忆。

每个 batch 都创建独立的 Agent Loop，不依赖持续增长的历史消息。如果没有术语表，
后续 Agent 无法知道前文如何翻译人物名、专名和核心概念，只能重新判断。术语表把这些
已经作出的选择带到后续 batch，使模型有机会保持一致。

在这一定位下，术语表有三个作用：

1. **提供历史译法**：告诉当前 Agent 前文曾如何处理相关表达；
2. **提供概念说明**：通过 note 补充该术语在书中的身份、语境或概念关系；
3. **降低重复判断成本**：避免每个独立 batch 都从零推断重要人物名和核心概念。

它不需要证明当前 source 与历史术语完全等价，也不需要保证 target 在每种语境下逐字
出现。即使检索出一个只是可能相关的术语，模型仍可结合当前原文判断是否采用。

这也改变了对误召回的评价：在硬校验场景下，误召回可能错误地阻止提交；在软提示场景
下，误召回通常只是在 prompt 中多提供一条参考，代价很低。

## 六、当前的最终方案

当前方案是“完整保存，按 batch 宽松检索，交给 LLM 遵循”。

### 保存

- `TranslationState.glossary_terms` 保存完整术语表；
- LLM 通过 `add_glossary_terms` 自主决定添加哪些术语；
- source 写入时仍做格式归一化后的精确去重；
- 不引入术语族、主从关系、自动合并和历史译文回滚。

### 检索

构造每个 `TranslationBatchInput` 时，将当前 batch 的全部 source 归一化并拼接，然后用
RapidFuzz 从完整术语表中筛选可能相关的已有术语：

```python
fuzz.partial_ratio(normalized_term_source, normalized_batch_text) >= 80
```

只有检索到的术语进入当前 batch，不再传递完整术语表。不限制 Top-K，不建立索引，
也不增加词法分析或二级规则。

该方法能够召回：

- `hegemony` → `hegemonic`：87.5；
- `late socialism` → `late-socialist`：85.7；
- `Lefort's paradox` → `Lefort’s paradox`：93.8。

它也会产生少量误召回，例如 `iterability` 命中 `the ability`、`eternal state` 命中
`several states`。这些误召回目前可以接受，因为术语只是软提示，不会触发提交失败或
强制重译。简单提高阈值又会漏掉需要的词形变化，所以当前保留 80。

### 使用

- 当前 batch 只看到检索到的已有术语；
- LLM 结合术语说明和具体语境完成翻译；
- `submit_translation` 只校验输出数量、类型和非空性，不校验术语字符串；
- 已提交译文不会因后续术语变化自动重译。

v1.2 使用该方案完整运行了 13 个 batch。最终术语表包含 42 项，每批实际提供 0 至
11 项术语，所有 batch 均成功提交，没有术语相关的提交失败。当前实验因此维持这一
轻量方案，不继续增加规则。
